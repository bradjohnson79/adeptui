## 8. Fix Adept UI Hosted Beta CORS — Live Runtime Repair

### Symptom
Chrome at `https://adeptui.vercel.app` reported `net::ERR_INSUFFICIENT_RESOURCES` for Studio API requests. Adept UI displayed `STUDIO_API_OFFLINE` while backend manager reported all services ONLINE.

### Root Cause
`studio-api/app/main.py` configured FastAPI `CORSMiddleware` with `allow_origins=["*"]` AND `allow_credentials=True`. The CORS spec forbids wildcard `*` when credentials are enabled — browsers reject such requests, producing the resource-exhaustion signature.

### Fixes
- **`studio-api/app/config.py`**: Added `cors_origins: str` field with default explicit origins:
  `https://adeptui.vercel.app,http://127.0.0.1:5173,http://localhost:5173,http://127.0.0.1:8760,http://localhost:8760`
- **`studio-api/app/main.py`**: Parse `settings.cors_origins` (comma-split) → `allow_origins` list, replacing `["*"]`.
- Configurable via `STUDIO_CORS_ORIGINS` env var.

### Verification
- `Invoke-WebRequest` with `Origin: https://adeptui.vercel.app` → `Access-Control-Allow-Origin: https://adeptui.vercel.app` for both GET and OPTIONS.
- `https://api-beta.adeptui.org/api/healthz` → 200
- `https://adeptui.vercel.app` → 200

## 10. Frontend Request Architecture Audit (Read-Only)

### Objective
Read-only architectural investigation of Adept UI's frontend-to-Studio-API communication. Diagnose why `https://adeptui.vercel.app` works initially but after several minutes Chrome produces `net::ERR_INSUFFICIENT_RESOURCES` against `/api/health`, `/api/capabilities`, `/api/gpu/stats`, etc., and Adept UI falsely reports `STUDIO_API_OFFLINE` while backend manager reports all services ONLINE.

### Scope
No code modified, no commits, no pushes. Investigated the `beta` branch (HEAD `35e572b`) — the deployed frontend source. The local checkout `feature/ai-guided-setup` does not contain the runtime architecture.

### Root Cause — CONFIRMED IN SOURCE AND REPRODUCED LIVE
**Unbounded emit→refetch feedback loop on `/api/health`** plus a **zombie probe defect** that breaks recovery.

1. `api.ts:939` — every successful `/api/health` response calls `markStudioApiHealthy()`.
2. `studioApiConnection.ts:255-264` — `markStudioApiHealthy()` emits unconditionally (no equality check in `setSnapshot`).
3. `useStudioHealth.ts:43-54` — every emit while CONNECTED fires a new `/api/health` request.
4. `useStudioHealth` mounted 3× on Home (AppChrome + SystemStatusStrip inside AppChrome + SystemStatusStrip at Home.tsx:653).
5. Each `/api/health` → emit → N subscribers each fire new request → exponential amplification, ratio N.

### Defect B — Zombie Probe
`probeStudioApiHealth()` clears `probeInFlight` only in the full-check `finally`, not after the fast `/api/healthz` success path. After first successful healthz, `probeInFlight` is a resolved promise forever. All scheduled backoff probes and Retry clicks return stale promise without network I/O. Monitor is blind to failures and cannot self-heal.

### Defect C — Suspension Flag Ignored by Chrome Pollers
`shouldSuspendDependentPolling()` honored only by `CoDirectorSession` and `useProductionDock`. `SystemStatusStrip` (15s), `BetaRuntimeStatus` (15s), `CapabilityStatusBadge` (30s) never check it.

### Live Measurement (5 minutes, Home page, no interaction)
| Elapsed | `/api/health` cumulative | Total | Failed | In-flight | Monitor state |
|---|---|---|---|---|---|
| T+12s | 260 | 271 | 0 | 259 | CONNECTED |
| T+84s | 3,270 | 3,317 | 448 | 1,350 | — |
| T+157s | 7,356 | 7,421 | 2,723 | 1,350 | RECONNECTING |
| T+229s | 11,328 | 11,413 | 5,003 | 1,350 | RECONNECTING |
| T+308s | 15,053 | 15,159 | 7,078 (47%) | 1,350 | RECONNECTING, banner visible |

- **Rate**: ~650/min → ~3,000-3,300/min sustained. **EXPONENTIAL until Chrome-capped**.
- In-flight pinned at 1,350 = Chrome per-origin pending-request ceiling → `net::ERR_INSUFFICIENT_RESOURCES`.
- `/api/healthz`: only 17 in 5 min (monitor zombied).
- JS heap flat at 39 MB — network-stack exhaustion, not memory.
- Backend healthy throughout (some requests succeed → `consecutiveFailures` oscillates at 1, never reaches terminal OFFLINE).
- Navigation test: no poller leaks; storm is chrome-global, not navigation-driven.

### Recommendation
**RECOMMENDATION — TARGETED POLLING REPAIR** (with minimal shared read layer)

1. `studioApiConnection.ts` — emit only on actual state change (equality check in `setSnapshot`).
2. `studioApiConnection.ts` — clear `probeInFlight` in one outer `finally` (kills zombie).
3. `useStudioHealth.ts` — refetch only on transitions into CONNECTED/RECOVERED + in-flight guard; consolidate to one instance.
4. `api.ts` — single-flight + 5-15s TTL cache for `/api/health`, `/api/capabilities`, `/api/gpu/stats`, `/api/runtime/beta`.
5. Chrome pollers — honor `shouldSuspendDependentPolling()`.

No full broker, no SSE rewrite. The central coordinator already exists with backoff, hysteresis, suspension flags, subscriber fan-out — it is 80% of a connection manager already built. What is missing is change-detection, a working probe, transition-only refetch, and single-flight/TTL for four read-mostly endpoints.

### Files That Would Need Modification (on `beta`)
`studio-web/src/runtime/studioApiConnection.ts`, `studio-web/src/hooks/useStudioHealth.ts`, `studio-web/src/api.ts`, `studio-web/src/components/dashboard/SystemStatusStrip.tsx`, `studio-web/src/components/dashboard/AppChrome.tsx`, `studio-web/src/pages/Home.tsx`, `studio-web/src/components/BetaRuntimeStatus.tsx`, `studio-web/src/components/CapabilityPanel.tsx`.
