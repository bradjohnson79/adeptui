## 1. What M3.0a was for

Two jobs. First, find out what this application actually does when nothing is mocked, and
write it down without flattering it. Second, integrate fal.ai as a real cloud render provider
under bring-your-own-key.

The first job is the reason the verdict is conditional. The audit found 94 mock and scaffold
findings, 9 of them CRITICAL, and the CRITICAL ones shared a single shape: a code path that
reported work as complete without doing it, reachable in production, sometimes triggerable by
the client. Those are now closed. What remains is not dishonesty but absence - real providers
that have never been run.

### 2.1 The three findings that matter most

**Nothing generative has been proven.** Eight of eighteen platforms carry NOT_TESTED or
PARTIAL in their provider or artifact column. Not one image, video, lipsync or audio artifact
was produced by a real provider during this milestone. ComfyUI is reachable on the audit
machine, which means a local proof is *possible*; it was not attempted, and a reachable
service is not a produced artifact.

**The studio job queue does not survive a restart.** `queue_worker.JobQueue` is an in-process
asyncio queue. Nothing re-reads `Job` rows left in `queued` or `running` at shutdown, so a
render interrupted by an API restart stays non-terminal in the database forever. Two
neighbouring subsystems do handle this correctly - the Production Executive calls
`recover_running_jobs` in `start()`, and the download queue has an explicit recovery step -
which is what makes the omission visible rather than theoretical. This is a real defect found
by reading `main.py`, not by any failing test, and no test covers it.

**The Co-Director cannot bypass anything.** 51 tools: 31 read, 20 mutating, and all 20
mutating tools are preview/apply pairs that produce an approval-gated proposal. There is no
approve tool, no job-enqueue tool, no shell, filesystem, SQL or eval tool, and no runtime
registration - a declared tool with no binding is an import-time crash. The model also cannot
request a fixture success, because the executive strips those fields from its payloads.

## 3. fal.ai

### 3.1 Connection and validation

`PUT /api/fal/key` probes fal before persisting. The probe is an authenticated GET against a
queue-status URL with a random request id: fal answers it without creating a job, so
validation is free and cannot spend credits. A key fal rejects is not stored, and the
endpoint returns the rejection.

| Behaviour | Status | Evidence |
|-----------|--------|----------|
| Rejects a key fal refuses, stores nothing | VERIFIED | `test_put_key_rejects_a_key_fal_refuses`; Playwright structural test 1 |
| Accepts a key fal approves | VERIFIED 2026-07-27 | `validate_fal_key` returned `verified` (HTTP 404) for the `.env` key during the C2 live proof |
| Validation spends no credits | VERIFIED by construction | Queue-status probe, no job submission |

### 3.4 Credential security

| Property | Status |
|----------|--------|
| Key encrypted at rest | VERIFIED - `secrets_store.py`, covered by `test_fal_credentials.py` |
| No endpoint returns the key | VERIFIED - `test_status_never_returns_the_key` plus two Playwright tests |
| No key material in the built frontend | VERIFIED - Playwright structural test 4 |
| Co-Director sees no key material, not even a mask | VERIFIED - `get_cloud_render_status` returns state and guidance only |

The Co-Director redaction is deliberately stricter than the settings API, which does return a
mask and fingerprint to the UI. Model output can be echoed into a transcript, so the model
gets the answer to "will cloud rendering work?" and nothing that identifies the credential.

### 3.5 Co-Director integration

`get_cloud_render_status` is the model's only window onto fal: provider, credential state,
usability, verification timestamp, engine list with media types, and one sentence of guidance
per state. It is read-only. There is no tool to set a key, submit a fal job, or choose an
engine.

### 3.6 Unresolved

1. Credential acceptance is unproven - only the rejection path is verified.
2. No fal render has ever run, so no fal artifact, failure or recovery path has been observed.
3. No fal image engine exists to integrate.
4. Usage and billing reads are untested.

## 8. Conditions

These are what stands between the current verdict and an unqualified READY.

**C1 - Produce one real local artifact.** Install a checkpoint, submit one
`POST /api/projects/{id}/imagegen`, and confirm the `Asset` row and the file on disk. This
closes the largest evidence gap in the wiring matrix and would move `image` from NOT_TESTED
to PASS in the provider and artifact columns. ComfyUI is already reachable, so this needs a
model and a deliberate run, nothing more.

**C2 - Produce one real fal artifact. PARTIALLY CLEARED 2026-07-27.** One budgeted live job
ran via `scripts/m30a_fal_budgeted_live_proof.py`: `fal_seedance` ->
`bytedance/seedance-2.0/text-to-video`, 4 s at 480p, request id
`019fa1fc-e05f-7d80-9908-e6d0c3e8d4fc`, artifact
`artifacts/m30a-fal/seedance_t2v_4s_480p.mp4` (667,974 bytes). The cloud path is no longer
verified only for how it fails. What remains: an **image-to-video** job with a real start
image, confirmation of the `Asset` row and `falRequestId` written by the queue worker rather
than by the proof script, and one observed live failure. See
[FAL_AI_REAL_JOB_RESULTS.md](./m3.0a/FAL_AI_REAL_JOB_RESULTS.md).

**C3 - Fix studio job queue restart recovery.** Add a recovery pass in the API lifespan that
re-enqueues or terminally fails `Job` rows left in `queued` or `running`, mirroring
`recover_running_jobs` in the Production Executive. Add the test that proves it - there is
none today. Until this lands, an interrupted render is lost silently, which is the one
remaining way this system can mislead a user without any mock being involved.

**C4 - Resolve the Bible-apply foreign-key failure.** Two Playwright specs fail because
applying an approved proposal raises `IntegrityError`. Whatever its origin, approval-gated
Bible writes are the core of the Co-Director safety model, and a broken apply path should not
cross into M3.0b unexplained.

**C5 - Enable the M2.9 and M2.14 flags in the E2E environment, or state why not.** Five of
the nine skips are flag-gated production UI. They are honest skips, but they mean the newest
production surfaces have almost no browser-level coverage.

C1 and the remainder of C2 are the ones that block a full green. C3 is a defect that should not ship. C4 and
C5 are quality gates on the evidence base rather than on the product.

## 9. Why not one of the other two verdicts

**Not READY FOR M3.0b.** No generative artifact has been produced by a real provider, locally
or on fal. The queue loses interrupted work. Claiming unqualified readiness would be exactly
the kind of unearned green this milestone existed to eliminate.

**Not NOT READY FOR M3.0b.** All 9 CRITICAL and 7 HIGH findings are closed, and every one of
them was closed by making the system refuse rather than lie. The full Playwright suite runs
at 89/104 with the single M3.0a-caused failure fixed, the backend suites are at 135/138 with
11 new refusal tests, credential security is verified on four independent axes, the Provider
Manifest is untouched, and the Co-Director provably cannot bypass a single approval gate. The
foundation is sound; what is missing is proof of output, and that is a run, not a rebuild.
