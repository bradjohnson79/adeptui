# 3. Global implementation rules

## 3.1 No mock production acceptance

Mocks may be used in unit tests and deterministic CI fixtures.

M2.9 section acceptance must not rely on mocked success where a real local production capability exists.

For each production section, record whether acceptance used:

```text
real local provider
real external provider
deterministic local processor
CI fixture provider
mock-only test
```

A section cannot be marked production-ready if its only working path is mock-only.

---

## 3.2 M2.7 owns durable execution

All long-running or failure-prone operations must run through M2.7 Production Jobs.

Examples:

```text
image.generate
frame.generate
video.generate
video.interpolate
video.validate
audio.generate
audio.process
lipsync.analyze
lipsync.generate
mouthtrack.generate
timeline.render
scene.render
edit.apply
music.generate
sfx.generate
```

Jobs must support:

- durable persistence;
- dependencies;
- retries;
- cancellation;
- restart recovery;
- progress;
- results;
- audit events;
- failure messages;
- linked assets;
- linked Production Context.

Do not introduce separate queues for image, audio, video, or rendering.

---

## 3.3 M2.5 owns visual validation

Visual outputs must use M2.5 validation where applicable.

Only the validation service may change visual-validation lifecycle state.

Do not clear:

```text
visualValidationPending
```

outside the M2.5 lifecycle.

M2.5 validation should be expanded where necessary to evaluate:

- image continuity;
- frame continuity;
- character identity;
- location consistency;
- camera compliance;
- Shot Profile compliance;
- mouth-region preservation;
- lip-sync visual quality;
- video continuity;
- edit continuity;
- final-scene continuity.

---

## 3.4 Human approval remains authoritative

Co-Director may:

- analyze;
- suggest;
- prepare;
- generate;
- compare;
- validate;
- recommend;
- create proposals.

Co-Director must not silently:

- approve assets;
- alter canon;
- replace timeline clips;
- accept a lip-sync take;
- commit editorial changes;
- publish a render;
- overwrite an approved voice;
- replace an approved music cue;
- mutate a Production Bible entry.

The system must distinguish:

```text
suggest
plan
preview
execute
review
approve
publish
```

---

## 3.5 Feature flags

Each major M2.9 production section must have a feature flag until accepted.

Feature flags default off unless explicitly authorized otherwise.

Flag-off behavior must verify:

- existing application remains functional;
- hidden routes are unavailable;
- no background job starts;
- no provider loads unnecessarily;
- no console errors occur;
- no migration requires the feature to be active.

# 6. Shared asset versioning

All production assets must use a consistent version model.

Assets must support:

```text
draft
generated
validation_pending
needs_review
approved
rejected
superseded
archived
```

Production Bible retrieval must return approved or explicitly requested historical versions.

- restore previous mouth rectangle;
- restore prior lip-sync take;
- restore previous music cue;
- restore approved image version;
- restore timeline version;
- revert a Co-Director proposal;
- roll back a failed render configuration.

Undo history must survive application restart where feasible.

At minimum, persisted revision history must allow restoration after restart.
