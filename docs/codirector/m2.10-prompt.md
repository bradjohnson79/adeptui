# 1. Milestone framing and M2.8 vs M2.10 distinction

M2.10 is **Capability Expansion**: Adept UI grows **beyond its native capabilities** via a disciplined pipeline. It must have a strict boundary so it does not become an endless feature-acquisition phase.

| Milestone | Role |
| --- | --- |
| **M2.8** | Builds the Model Radar, compatibility intelligence, sandboxing, routing, approval, and promotion architecture. |
| **M2.9** | Completes the native production platform (wired to available native capabilities; Accepted with documented limitations). |
| **M2.10** | Capability Expansion — Discover → Evaluate → Sandbox → Integrate → Promote → Feature Freeze. |
| **M3.0** | Proves frozen v1.1 end to end through full qualification. |

```text
M2.8 builds the machinery.
M2.9 completes the native platform.
M2.10 expands beyond native via disciplined discovery→promotion.
M3.0 proves frozen v1.1 end to end.
```

# 2. Primary objective

**Purpose:** Adept UI grows beyond its native capabilities.

Pipeline emphasis (preserve staged approvals and all existing hard stops):

```text
Discover → Evaluate → Sandbox → Integrate → Promote → Feature Freeze
```

Allow Co-Director to scan GitHub, Hugging Face, plugins, providers, nodes, and models for valuable production expansions; evaluate them against the frozen Native Capability Snapshot and Adept UI architecture; present qualified candidates for approval; install approved candidates into isolated sandboxes; validate them; wire selected additions into the appropriate production sections; and promote only accepted integrations into Adept UI v1.1 — only with staged human approvals at every gate.

Compare each candidate to the frozen native snapshot to decide: **fills missing** / **improves** / **duplicates** / **reject**.

This is different from M2.8: M2.8 builds the discovery and integration intelligence; M2.10 uses it for Capability Expansion.

No discovered add-on should go directly from search results into the production environment.
**Discovery is not authorized yet** — status remains planning / awaiting readiness + Product authorization.

---

# 3. Recommended workflow chain

```text
Discover
-> Evaluate (relevance, compatibility, license/trust, duplicate vs native snapshot, impact)
-> Sandbox (install isolated; technical + production-quality validation)
-> Integrate (wire end to end; section-level acceptance)
-> Promote (v1.1 candidate; staged human approvals)
-> Feature Freeze
```

Detailed chain (same hard stops):

```text
scan
-> discover candidate
-> classify capability
-> evaluate relevance
-> evaluate compatibility
-> check license and trust
-> compare to frozen Native Capability Snapshot (fill / improve / duplicate / reject)
-> estimate installation impact
-> create admin/operator proposal
-> receive approval
-> install into isolated sandbox
-> run technical validation
-> run production-quality evaluation
-> propose Adept UI integration
-> wire capability end to end
-> run section-level acceptance
-> promote into v1.1 candidate
-> Feature Freeze
```

Inspect ≠ download ≠ execute ≠ integrate ≠ promote. Each stage requires its own explicit human decision.

# 5. Six evaluation dimensions

Every discovered add-on must receive a structured score across these dimensions.

## 5.1 Production value

Does it improve a real filmmaking workflow?

- Critical
- High value
- Useful
- Experimental
- Redundant
- Out of scope

## 5.2 Compatibility

Evaluate:

- Windows support
- Python version
- CUDA version
- PyTorch version
- ComfyUI compatibility
- VRAM requirement
- storage requirement
- RTX 5090 support
- required custom nodes
- model architecture
- workflow adapter needs
- conflicting packages

## 5.3 Trust and maintenance

Evaluate:

- official versus community
- repository activity
- release history
- issue response
- maintainers
- stars and usage as weak signals only
- signed or hashed releases where available
- dependency quality
- suspicious install scripts
- binary provenance
- known vulnerabilities

Popularity alone must not establish trust.

## 5.4 Licensing

Record:

- code license
- model license
- commercial-use rights
- redistribution rights
- cloud-use restrictions
- attribution requirements
- research-only restrictions
- gated-access terms
- generated-output restrictions

A technically compatible add-on may still be unacceptable for Adept FilmWorks.

## 5.5 Architectural fit

Determine whether the candidate:

- duplicates an existing capability
- improves an existing capability
- replaces an inferior provider
- requires a new capability contract
- can use the current M2.7 job system
- can be validated through M2.5
- can provide complete provenance
- supports the current approval model
- can be represented in the Capability Registry

See [capability-contract-reference.md](./capability-contract-reference.md).

## 5.6 Quality improvement

A candidate must prove measurable production value. Examples:

- stronger identity retention
- better location continuity
- cleaner camera control
- better temporal stability
- faster generation
- lower VRAM
- more precise mouth control
- higher-quality SFX
- better dialogue isolation
- more reliable timeline metadata

- Dismiss
- Watch
- Research further
- Approve sandbox evaluation
- Reject sandbox evaluation

- Reject integration planning

# 10. End-to-end integration requirement

A candidate is not accepted merely because it runs in the sandbox.

It must be wired through the real Adept UI stack:

```text
Capability Registry
-> provider adapter
-> workflow adapter
-> Co-Director routing
-> M2.7 job handler
-> production workspace
-> asset persistence
-> generation manifest
-> validation
-> review
-> approval
-> Director Timeline or Production Bible handoff
```

Every integrated add-on must support the same system contracts as native production tools. Capability IDs, providers, workflows, validators, processors, routing/approval/versioning, flags, and job handlers are defined in [capability-contract-reference.md](./capability-contract-reference.md). Category readiness gaps are tracked in [m2.10-addon-integration-contracts.md](./m2.10-addon-integration-contracts.md).

# 11. Integration categories

An accepted candidate may become one of:

| Category | Meaning | Examples |
| --- | --- | --- |
| **Provider** | A complete alternative generation backend | `video.generate` provider; `audio.sfx.generate` provider; `lipsync.generate` provider |
| **Workflow adapter** | A new workflow using an already supported runtime | ComfyUI location consistency workflow; ComfyUI mouth-only correction workflow |
| **Processor** | A deterministic local production tool | audio cleanup; frame interpolation; scene detection; mouth tracking |
| **Validator** | An additional production-quality check | temporal flicker validator; mouth-region validator; audio clipping validator |
| **Co-Director intelligence source** | Improves analysis, retrieval, or planning | Must never bypass Co-Director existing approval and orchestration systems |

# 13. Scope control

This milestone could expand indefinitely; it requires a stop condition.

Recommended limits:

- Maximum number of promoted add-ons
- Maximum milestone duration
- Maximum candidates per production department
- Required production-value threshold

Practical structure for this cycle:

- scan all major production departments
- shortlist no more than **three** candidates per department
- sandbox only the strongest candidates
- promote only candidates that clearly improve the existing suite
- defer experimental candidates to a future add-on cycle

The purpose is not to install everything available. The purpose is to make Adept UI v1.1 stronger without destabilizing the platform before M3.0.

# 18. Hard constraints

- M2.10 must use M2.8 discovery/compatibility/sandbox/approval/routing/promotion architecture.
