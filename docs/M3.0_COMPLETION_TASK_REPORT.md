## 4. The fal `.env` bridge

`studio-api/app/fal_env_bridge.py`, awaited from the FastAPI lifespan, removes a real
contradiction: `m29.providers.fal_key_present` read the secret store *then* the environment,
while the queue worker's fal render read the secret store only. A `.env`-only key therefore
made diagnostics say "ready" and the render say "not configured".

The bridge never overwrites a stored key, probes a candidate with
`fal_client.validate_fal_key` (a 404-expecting request id - no job, no billing), stores on
acceptance, stores-but-flags-unverified when fal is unreachable, and stores nothing on a 401
or 403. `STUDIO_FAL_ENV_BRIDGE=0` disables it, and it is set to `0` in `tests/conftest.py`
and `scripts/e2e-start.mjs` so no test or E2E boot makes a live call.

Nothing logs the key. `set_secret_verification` strips `key` and `api_key` from any detail
dict before writing, and a test asserts the key appears in no report, no verification record,
and no file in the secrets directory.

## 9. Verdict reasoning

### M3.0a - ACCEPTED

Every one of M3.0a's five conditions now has evidence behind it:

| Condition | State |
|-----------|-------|
| C1 - one real local artifact | **Cleared.** Z-Image PNG, checksummed, with `Asset`/`AssetVersion`/`Job` rows |
| C2 - one real fal artifact under BYOK | **Cleared at the provider level and now inside the app.** Real paid render in M3.0a; registered as a project `Asset` with intact provenance here. The queue-worker write-back remains unproven (residual 4 above) |
| C3 - queue restart recovery | **Cleared.** Implemented, lifespan-wired, 7 tests |
| C4 - Bible-apply Playwright failure | **Cleared.** Green |
| C5 - M2.9 / M2.14 flags in E2E coverage | **Cleared.** E2E stack enables them; a runtime flag control makes ON and OFF both testable |

Add a fully green browser suite, an unchanged Provider Manifest, and a clean secret audit,
and the question M3.0a asked - *is the machine real and does it tell the truth about itself* -
is answered yes. The residuals in section 8 are absences and coverage gaps, not false claims.
That distinction is the one M3.0a itself drew, and it is why this reads ACCEPTED rather than
PARTIALLY ACCEPTED.

A reviewer who requires a fal render to have travelled through the Studio queue, or who
requires the backend suite to be green before any acceptance, should read this as PARTIALLY
ACCEPTED. Both objections are legitimate; both are named above rather than buried.

### M3.0b - NOT READY FOR MANUAL USER BETA

Zero of twelve situations executed. The plan's own instruction is not to use "WITH
CONDITIONS" when the core promise fails, and the core promise of M3.0b is that a filmmaker
can run a situation and keep the result. Nobody can, in any of the twelve.

"READY WITH CONDITIONS" was considered for a tightly scoped beta - still images only, local
ComfyUI only, audio by import - and rejected. A beta scoped that narrowly would not be
testing the Co-Director; it would be testing an image button. The feedback would be about a
product that does not exist yet, which is exactly the failure mode M3.0b was created to avoid.
